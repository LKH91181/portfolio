5. round3：登录链路补测（压测脚本参数逆向）

5.1 触发与脚本逆向结论

触发：用户提供压测脚本 OPS_connect0826.py（0826 版），要求按脚本参数重新梳理测试用例并完成测试。

对脚本的逆向结论（产物 workflow/login_helper.py 严格对齐其协议实现）：

  • OPS 服务真正的客户端登录是 WebSocket 注册式：入口 ws://192.168.66.232:10001，文本帧格式 = opcode + JSON 字符串；
  • 61100：连接建立后服务端主动推送的就绪信号（无需请求），脚本以单读取者事件承接；
  • 61001 = "登录"：发送 {"RpcId","ClientId","roomId","ClientType"} 即完成注册（无需任何凭证），响应为 PascalCase（Error/RpcId/Message/Key/AccountId 等）；
  • 61901 = 心跳：每 5s 发送一次保活；
  • clientId 由客户端自生成（uuid4().hex[:16]），服务端不签发、不校验来源；
  • 脚本参数：roomId=01272aa6-3c6d-4c10-89e7-8a4e9b65db1a（手术间23/zxsss23，经 tc_r3_008 响应证实）、ClientType=113。

根因解释：round2 中 5 条用例 missing_client_id 跳过的根因至此查明——此前误将 /api/ds/login 等 HTTP 登录接口当作客户端唯一登录入口，而这些接口只是门口屏管理端专用；普通客户端的凭证来自 WS 注册（连接即得 clientId，61001 即完成登录）。

6.3 f_ws_noverify（高危 · round3 实证）

  • 标题：WS 61001 登录零校验——任意 roomId（含全零 GUID）与越界 ClientType=999 均返回 Error=0「登录成功」，全程无凭证、无签名、无白名单。
  • 状态：round3 实证（tc_r3_003 / tc_r3_004，独立短连接各一次）。
  • 实证证据：roomId=00000000-0000-0000-0000-000000000000（不存在的术间）→ Error=0「登录成功」（应拒绝未拒绝）；ClientType=999（枚举外，合法域 100~123/200/201/210）→ Error=0「登录成功」。clientId 由客户端自生成（uuid4().hex[:16]）即被服务端接受，登录响应的 Key/AccountId 字段恒空。
  • 影响：结合 f_003（HTTP 无鉴权广播）说明系统身份体系完全自声明——任意内网主机可伪装任意客户端类型/任意术间接入，并调用全部 HTTP 接口（tc_r3_008/011/012 证实 WS 注册的 clientId 即被 HTTP 端点认可并可取回真实业务数据）。
  • 修复建议：61001 增加凭证或预共享密钥；服务端校验 roomId 存在性与 ClientType 枚举合法域（100~123/200/201/210）；登录响应的 Key/AccountId 字段当前恒空，可承载服务端签发凭证。
